### 2.4 巨型单元的处理结论

- `RunSession` 保持单局唯一权威，不拆成多个可独立提交的 authority；只抽纯 planner/协作者和只读模型缓存。
- `SkillExecutor` 保留技能释放事务权威；拆阶段和 Port，不把法力、冷却或成功事件分散到 Player/VFX。
- `RunOverlayInterface`（约 2190 行）与 `CombatHUD`（约 1312 行）本轮不做全面拆类。它们不是本轮证据最强的热路径，且大改会扩大 UI 回归面；只允许在 Task37 做由公共 API 迁移直接要求的最小适配。
- `SkillVfxCoordinator` 不成为玩法权威；只消费已提交事件和不可变表现快照。

唯一允许的依赖方向：

1. contracts/ports 不依赖具体 Node、UI、VFX、Growth 内部或可变资源；
2. 物理查询、PackedScene 实例化、持久化、SceneTree 和表现是 adapter；
3. 领域 authority 只依赖 Port，不读取 adapter 私有字段；
4. Host/Player 是接线边界，不复制领域规则；
5. UI/VFX 只能读不可变 Snapshot/Result/Event，失败不能回滚玩法事务；
6. 没有全局事件总线、Service Locator、新 Autoload 或全局可变缓存。

## 4. 冻结的稳定接口

### 4.1 同步弹道查询

| 类型 | 最小字段/方法 | 约束 |
| --- | --- | --- |
| `ProjectileSweepProfile2D` | `shape`、`speed`、`max_distance`、hurtbox/block masks、margin、wall tie、max contacts | Resource 只作静态配置；运行请求复制/只读 |
| `ProjectileSweepRequest2D` | world/space 上下文、起点 transform、归一方向、distance、profile、施法者/队伍/排除对象 | 构造后不可变；无合法上下文即拒绝 |
| `ProjectileSweepResult2D` | `status`、contact point、distance/fraction、合法 Hurtbox、stable id | status 至少含 enemy、blocker、no contact、invalid context、query failed |
| `ProjectileSweepQueryPort2D` | `query_first_contact(request) -> ProjectileSweepResult2D` | 同输入稳定；不创建飞行 Node |
| `PhysicsProjectileSweepQuery2D` | Port 的 Godot Physics 适配器 | 抽取当前 ProjectileDelivery 的 initial/cast/rest/probe/stable sort/墙 tie 规则；每个消费者实例最多持有 4 个可复用查询参数 scratch，逐次完整覆写 |

正式 profile 必须由 `scenes/element_projectile.tscn` 与元素爆发共同引用。现有正式参数为圆形逻辑 shape、`speed=720`、`max_distance=850`、hurtbox mask `8`、block mask `4`、margin `0.01`、wall tie `0.02`；Task34 迁移前后逐字段断言，禁止改值。

### 4.2 公共施法与预提交交付

```gdscript
SkillExecutor.try_cast(skill: SkillDefinition, slot_id: StringName = &"") -> CastAttemptResult
SkillDeliveryPreparePort.prepare(snapshot, spawn_snapshot) -> SkillExecutionCommitTransaction
```

`_try_cast_configured`、`_try_cast_locked` 继续是实现细节。`SkillExecutionServices` 以窄 setter 或 copy-with 保留所有已配置 Port；配置回收表现不得覆盖弹道查询或交付 prepare Port。

Task34 后元素爆发的唯一事务顺序：

```text
基本配置/控制状态/槽位/元素/SP/冷却校验
→ 锁定 CastSnapshot 与等级效果
→ 同步 sweep 查询
→ 仅 enemy contact：锁定 impact point
→ 离树实例化并完整 configure 爆发 Delivery，得到可提交事务
→ 再次检查提交前不变量
→ 提交外部事务
→ 扣 SP
→ 写冷却/元素/执行态
→ 发 accepted/activated/success 事件
```

查询或交付准备失败发生在提交点之前；失败结果不得含已提交 execution snapshot。所有成功事件仍在状态提交后发出，嵌套施法保护和既有事件顺序不得改变。

### 4.3 内容读取接口

静态 `RunContentCatalog` 只在组合阶段校验和编译，输出两个互不反向依赖的视图：

- `CombatSkillCatalogPort`：按 ID 返回 Combat 定义、固定普攻、可装备集合、runtime delivery 描述；
- `RunSkillContentPort`：按 ID 返回 Growth 自有的不可变 `RunSkillContentSnapshot`，以及有序商店/初始拥有/等级效果投影；
- `CompiledRunContentViews`：只由组合根持有，用于把两个 Port 分发给各自领域，不成为新运行权威。

所有返回集合复制或只读封装；索引容量精确受源 skill/relic 数量约束。源 Resource 在一局开始后被修改属于不支持行为，必须重新 compile，不能“实时同步”可变数组。

### 4.4 RunSession 读取与命令边界

```gdscript
RunSession.snapshot() -> RunSnapshot              # 同 revision 返回同一不可变对象
RunSessionHost.current_snapshot() -> RunSnapshot  # 集成层唯一读取入口
RunSessionHost.<typed_command>(...) -> RunCommandResult
```

RunSession 仍是唯一提交者。planner 只接收快照/值对象并返回不可变计划，不保存外部可变状态、不增 revision、不发信号。RunSession 校验计划与当前 revision 后原子提交，并保持原有通知顺序。

快照缓存规则：

- 缓存拥有者唯一为 RunSession；容量恒为 0 或 1；
- 第一次读取某 revision 构建一次，之后返回同一只读实例；
- 每个成功状态改变只失效一次；拒绝、完全相同的幂等重放和无状态变化不失效；
- 任何数组/Dictionary getter 继续返回副本或不可变值，调用者不能污染缓存；
- 存档迁移读取旧快照的字段和值不变，不以对象 identity 作为存档语义。

### 4.5 表现与瞬态生命周期

- 回收 prepare/transaction 暴露 `Array[ElementReclaimPresentationTargetSnapshot]` 或等价不可变读取方法；VFX 不再 `get()` 私有字段。
- `RunRoomTransientDeliveryRegistry` 或等价的 Host-owned 有界注册表只登记当前房的动态交付；房间切换按登记项清理，节点退树时自动注销。
- 正式遗物为 `DISABLED` 时 Host 不启用连续 RunSession tick；启用旧兼容模式时才调用公共 `advance_continuous(delta)`，状态改变仍由 RunSession 发快照事件。

### 9.3 权威、计划与缓存迁移

1. 给现有购买、升级、重置、即时配装、离店、路线、房间切换、胜负和重放建立 command trace golden：结果 reason/detail、revision、通知、经济守恒、库存/槽/路线字段逐项锁定。
2. 抽出的 planner 是纯函数式协作者：输入不可变快照、命令值和 Port 读取结果，输出 typed plan/rejection；不持有 `RunEconomyState`、`SkillInventoryState`、RuntimeLoadout 或 SceneTree。
3. `RunSession` 独占可变 state、replay ledger、revision、commit 和 signal；依次验证 expected revision/command fingerprint、调用 planner、验证计划、提交各 state、增 revision、缓存失效、构造/取得新 snapshot、发原有 signal。不得让 planner 直接 commit。
4. 先抽 shop/economy，再 loadout，再 flow；每一步单独复跑 golden，避免一次性重写 1189 行。
5. `RunFlowDefinition.compile()` 或等价 compiler 在原有 validation 成功后生成 `CompiledRunFlowDefinition`，包含 node ID index 和冻结的有序节点/边；`RunDirector` 运行期只使用 compiled view。
6. `RunSession.snapshot()` 加单对象缓存。任何成功 mutation 在第一次后续读取前不得构建多份；拒绝、幂等重放、正式禁用系统的 no-op 不失效。
7. snapshot 子集合仍不可外部修改；两个并行 RunSession 绝不共享缓存、planner state 或 replay ledger。

RunSession 可以因可读性下降而保留少量短 wrapper，但禁止把同一事务拆成多个 authority 或引入跨协作者共享可变 Dictionary。

### 9.4 专项性能门禁 `perf_run_read_model_v1`

固定两组：

- 读取组：同一 revision 连续 100000 次 `snapshot()`，再执行 1000 条固定 accepted/rejected/replayed 命令轨迹，每条后读取 10 次；
- 流程组：16/64/256 节点合法图，各 100000 个固定 node ID 查询，加一条正式六战完整 trace。

主计数：RunSnapshot/子快照构建、cache invalidation、source node 比较、planner 构建/commit、revision/signal。通过阈值：

- 同 revision 完整 RunSnapshot 构建精确 ≤1；每个真实成功 mutation 恰好一次失效，拒绝/幂等/no-op 为 0；
- flow 运行查询不扫描源 nodes，index probe 记为常数 1；
- cache 容量恒 ≤1/RunSession，flow index entry 精确等于唯一 node 数；
- 读取组 median 至少改善 30%；流程组 median 至少改善 20%；p95 均不回退超过 10%；
- 命令结果、revision、signal 计数、完整 trace 快照与 before 逐字段相同。
