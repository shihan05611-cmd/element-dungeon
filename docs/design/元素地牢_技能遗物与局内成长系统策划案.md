# 《元素地牢》技能、遗物与局内成长系统策划案

> 状态：本轮实现基线。本文以当前已完成的水火战斗 MVP 为前提；如与旧版策划冲突，以本文为准。
>
> 技能栏、CurrentElement 和释放事务的冻结细则见 docs/design/共享技能槽与元素释放规则.md。

## 1. 系统目标

当前阶段新增三条局内成长线：

- 技能：决定玩家本局可以执行哪些主动行为。
- 遗物：围绕现有能力形成有条件的构筑效果。
- 角色等级与属性：提供稳定的纵向成长。

本轮明确不制作：

- 技能等级、技能重复升级或技能升级表。
- 术式、装备、遗物品质、遗物升级和随机词条。
- 商店购买、出售和货币。
- 土、电、元素容量变化或元素反应公式变化。
- 复杂房间类型和跨局永久成长。

## 2. 核心冻结规则

### 2.1 技能没有等级

技能在本局只有以下状态：

```text
未拥有 → 已拥有 → 已装备或未装备
```

- 同一技能每局最多获得一次。
- 已拥有技能不再进入技能奖励池。
- 技能被替换或卸下后仍然属于本局已拥有技能。
- `SkillDefinition` 始终是静态只读配置，不保存拥有、装备或运行时状态。
- 不创建 `SkillInstance.level`、升级表或按等级解析后的技能定义。

### 2.2 只有角色等级

- 经验达到要求后立即提升角色等级。
- 每升一级获得 1 个未分配属性点。
- 一次获得大量经验时允许连续提升多级。
- 战斗中不能分配属性点，只能在商店整备阶段提交。
- 角色等级本身不直接修改战斗数值；数值只来自已分配属性点。

### 2.3 静态配置与运行时状态分离

- Resource 只保存静态定义、目录和房间配置。
- 本局状态只保存稳定 ID、整数、布尔值和不可变快照。
- 本局状态不得保存 Player、CombatReceiver、ElementCarrier 等 Node 引用。
- 不直接修改共享的 `SkillLoadout`、`SkillDefinition` 或 `RelicDefinition` Resource。

## 3. 房间流程

首版只使用普通战斗模板，通过奖励类型区分房间：

```text
开始本局
↓
普通战斗房间 1
↓
固定技能三选一
↓
选择下一房间：技能奖励 / 遗物奖励
↓
完成战斗并领取对应奖励
↓
继续选择下一房间
↓
第 3 个战斗房间后进入商店
↓
分配属性点、调整技能槽并确认
↓
房间 4～6
↓
第 6 个战斗房间后进入商店并结束原型
```

房间流程使用明确状态机：

```text
COMBAT → REWARD → ROUTE_CHOICE → COMBAT
                          ↓
                         SHOP → COMBAT / RUN_COMPLETE
```

任何 UI 只能请求状态迁移，不能自行宣布房间完成、发放奖励或提交商店结果。

## 4. 技能拥有与装备

### 4.1 初始配置

- 普通近战固定拥有，不进入奖励池，也不能卸下。
- 元素弹初始拥有，水火形态均可装备。
- 全元素共享唯一一套 3 个主动位置和 1 个被动位置。
- 固定普通攻击位于共享技能栏之外。
- 主动位置允许装备主动或被动；被动位置只允许被动。
- 允许 0 主动 + 4 被动，但配装界面必须显示风险提示。
- 元素变化不改变槽位内容，同一按键始终对应同一技能 ID。

### 4.2 技能类型

技能分类由两个正交维度组成：

| 行为类型 | 规则 |
| --- | --- |
| 主动 | 可由主动位置按键请求释放 |
| 被动 | 装备后持续生效，不能发起释放 |

| 元素策略 | 规则 |
| --- | --- |
| 元素专属 | 接受释放时自动切换到固定元素并锁定 |
| 通用元素 | 接受释放时读取并锁定 CurrentElement |
| 无属性 | 不切换元素，锁定元素为 NONE |

技能拥有状态与槽位状态彼此独立；槽位只保存技能 ID，不拥有技能本身。

专属技能可以从其他元素状态请求释放，只有通过全部验证并被接受后才自动切换。

### 4.3 技能奖励

- 第一关从初始技能池生成 3 个未拥有技能；不足 3 个视为配置错误，不得用重复技能补位。
- 后续技能奖励最多提供 3 个合法、未拥有的选择。
- 不出现已拥有技能、未开放元素的专属技能或当前规则下完全无法装备的技能。
- 奖励生成后保存为 `PendingReward`，关闭再打开界面不能重新随机。
- 技能池没有合法候选时，路线生成器不得继续提供技能奖励房。
- 获得技能后可以立即请求装备；装备失败不影响技能已经获得的事实。

### 4.4 释放与反应冻结规则

- 玩家只有一个权威 `CurrentElement`；元素变化不改变共享技能栏。
- 专属技能通过全部验证并在接受释放时才自动切换；失败释放不切换、不扣资源、不进入冷却。
- 通用元素、无属性及已经生成的攻击均使用接受时的元素快照，不读取之后的实时元素。
- 水火反应倍率固定为 `1 + 实际消耗层数 × 30%`，只按实际消耗层数计算。

## 5. 遗物系统

### 5.1 规则

- 遗物是本局持续生效的全局被动，不安装到具体技能。
- 同名遗物每局最多获得一次。
- 没有装备槽、品质、等级和随机词条。
- 遗物优先提供条件效果，不以大量堆叠基础数值为主要方向。
- 首批遗物不得修改每层反应倍率、元素容量和元素结算公式。

### 5.2 首批方向

- 基础属性：提高最大生命、最大能量或少量基础伤害。
- 形态切换：下一次技能减耗、交替形态奖励、带内部间隔的能量恢复。
- 元素反应：达到消耗阈值恢复能量、反应击杀恢复、反应后短暂强化普通攻击。
- 房间续航：房间完成恢复、每房首次低生命恢复、无伤完成额外经验。

### 5.3 技术边界

- `RelicDefinition` 保存静态显示信息、效果类型和参数。
- `RelicRuntimeState` 保存本局内部冷却、次数等运行时数据。
- 每类效果由小型 `RelicEffect` 策略实现；首版不建立万能触发条件 DSL。
- 遗物通过窄接口请求恢复、治疗或临时属性修正，不直接查找 Player 或战斗组件。
- 遗物只消费类型化事件，例如形态切换、已提交战斗结果、击杀和房间完成。

## 6. 经验、等级与属性

### 6.1 经验来源

```text
敌人击杀经验 + 房间完成经验 + 遗物条件奖励
```

- 技能房和遗物房提供相同基础经验效率。
- 房间完成经验用于稳定不同敌人组合下的升级节奏。
- 击杀和房间经验只能由 RunSession 接受一次，必须有稳定事件身份用于去重。

### 6.2 HUD

HUD 显示：

- 当前角色等级。
- 当前经验与下一级所需经验。
- 未分配属性点数量。
- 存在未分配属性点时的明确提示。

### 6.3 首版属性

| 属性 | 每点效果 |
| --- | --- |
| 攻击 | 基础攻击倍率 +5% |
| 体质 | 最大生命 +10 |
| 能量 | 最大能量 +5 |

攻击属性进入当前已有的施法者攻击快照，并在元素反应倍率之前生效：

```text
技能基础伤害 × 攻击属性倍率 × 元素反应倍率 - 目标固定防御
```

商店确认增加最大生命或最大能量时，当前值增加相同的最大值增量，不进行完全恢复。

## 7. 商店整备

首版商店没有货币，只提供：

- 分配未使用属性点。
- 查看遗物和已拥有技能。
- 调整唯一的共享技能栏。
- 预览本次变化并确认。

商店使用 `ShopDraft`：

1. 进入商店时从本局状态创建草稿。
2. 所有加点和换装只修改草稿。
3. UI 随时可以撤销未确认修改或恢复为进入商店时状态。
4. 确认时整体校验并一次提交。
5. 提交成功后本次属性分配不可撤回；失败时本局状态保持不变。

## 8. 运行时结构

`RunSession` 是本局领域门面，不是容纳全部逻辑的巨型对象：

```text
RunSession
├── ProgressionState
│   ├── level
│   ├── experience
│   ├── unspent_stat_points
│   └── allocated_stats
├── SkillInventoryState
│   └── owned_skill_ids
├── RuntimeLoadoutState
│   └── slot_id → skill_id
├── RelicInventoryState
│   ├── owned_relic_ids
│   └── relic_runtime_states
├── RouteState
│   ├── completed_combat_rooms
│   ├── current_phase
│   └── next_room_options
└── PendingReward
```

### 8.1 服务边界

- `ExperienceService`：计算升级，不接触 HUD 或玩家节点。
- `RewardGenerator`：输入本局只读快照、房间上下文和随机种子，输出不可变奖励提案。
- `RuntimeLoadoutState`：保存本局槽位映射，不修改初始 Loadout Resource。
- `RelicController`：管理已拥有遗物和运行时效果实例。
- `RunDirector`：执行房间流程状态机，不计算伤害或技能合法性。
- `PlayerGrowthAdapter`：由集成层实现，把已提交属性快照应用到现有玩家组件。

### 8.2 事件边界

- 事件流属于单个 RunSession，不使用全局字符串 EventBus。
- 事件使用明确 DTO，禁止用任意 Dictionary 传递关键数据。
- 战斗事件只读取已经提交的 `CombatResult`。
- 奖励、遗物和 RunDirector 不直接修改 `CombatReceiver` 或 `ElementCarrier`。

## 9. 原型内容规模

| 内容 | 数量 |
| --- | ---: |
| 固定普通攻击 | 1 |
| 初始通用技能 | 1 |
| 可获取技能 | 6～8 |
| 遗物 | 8～12 |
| 属性 | 3 |
| 普通战斗房间 | 6 |
| 商店节点 | 2 |
| 单次奖励选项 | 最多 3 |

首个实现检查点只需要少量占位内容跑通“战斗 → 奖励 → 角色升级 → 商店确认 → 下一房间”，系统边界验收通过后再扩充内容数量。

## 10. Agent 边界

- Agent E：成长领域核心，以及共享 Loadout 快照、元素变化事件和遗物筛选契约。
- Agent B：共享 3+1 技能栏、主动/被动分类、CurrentElement、自动切换与释放事务。
- Agent C：锁定元素的 Delivery 生命周期、多段/延迟攻击和池复用安全。
- Agent D：Player、HUD、配装、奖励/商店界面、测试房间与端到端集成。
- Agent A：本轮冻结；只有公共战斗结果确实缺字段时才允许由 A 增量修改。
