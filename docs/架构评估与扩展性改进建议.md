# 元素地牢 4.7 — 架构评估与扩展性改进建议

> 评估日期：2026-07-31  
> 评估范围：已实现系统（战斗、技能、成长、遗物、元素反应）  
> 掠过：遗物占位部分、未实现的关卡/房间系统

---

## 一、总体评分

| 维度 | 评分 | 说明 |
|------|------|------|
| **高内聚** | ⭐⭐⭐⭐☆ (4/5) | 各子系统职责清晰，数据/运行时分离优秀 |
| **低耦合** | ⭐⭐⭐☆☆ (3/5) | 核心框架解耦良好，但 Player 和 Catalog 存在"上帝类"倾向 |
| **可扩展性** | ⭐⭐⭐☆☆ (3/5) | 新增技能需改多处代码，批量配置能力不足 |
| **数据驱动程度** | ⭐⭐⭐⭐☆ (4/5) | 技能/遗物均为 Resource 数据驱动，但注册仍手动 |

**总评：良好的架构基础，但有显著提升空间。** 当前架构已经比大多数 Godot 项目更规范（contracts 层、polymorphic execution、signal 通信），主要问题集中在"新增内容时的摩擦成本"。

## 二、做得好的地方（保持不动）

### 2.1 技能三层架构 — 优秀 ✅

```
SkillContentDefinition (.tres)   ← 展示/获取元数据
    └─ gameplay_definition: SkillDefinition (.tres)   ← 施放策略/冷却/能量
            └─ execution_definition: SkillExecutionDefinition (.tres)   ← 具体执行
                    └─ payload: AttackPayloadDefinition (.tres)   ← 伤害/元素配置
```

每层职责单一，新增一个技能理论上只需创建 `.tres` 资源文件。这是整个项目最出色的设计。

### 2.2 Contract 数据对象层 — 优秀 ✅

`combat/contracts/` 下所有数据对象（`CastSnapshot`、`CombatResult`、`DamageResolution` 等）都是不可变的纯数据载体，不包含任何业务逻辑。这确保了跨子系统通信的边界清晰。

### 2.3 Delivery 生命周期管理 — 优秀 ✅

`DeliveryBase` 提供了完整的初始化→运行→清理→复用协议：
- `initialize()` 在入树前调用，防止状态污染
- `prepare_for_reuse()` 支持对象池化
- `_submit_hurtbox_hit()` 内置去重（同一 hit_index 不重复命中同一 receiver）

### 2.4 信号驱动的组件通信 — 良好 ✅

`SkillExecutor` 通过信号（`cast_started`、`phase_changed`、`execution_ended`）通知外部，而非直接调用 Player 方法。`SkillController` 作为 facade 进一步隔离了内部复杂性。

### 2.5 遗物系统的 Port 模式 — 良好 ✅

`GrowthEffectPort` 抽象了遗物效果对游戏世界的操作接口，`PlayerGrowthAdapter` 是其具体实现。遗物效果不需要知道 Player 的存在，只依赖 Port 接口。

### 2.6 无状态解析器 — 良好 ✅

`DamageResolver`、`WaterFireResolver` 都是纯函数（static func resolve），无副作用，易于测试和推理。

## 三、存在的问题与改进建议

### 问题 1：Player 是"上帝类"（530行，耦合过紧）

**现状：** `player.gd` 直接引用了 6 个子节点组件、硬编码了 delivery 场景类型判断（`is ELEMENT_RAGE_DELIVERY_SCRIPT` / `is ELEMENT_BEAM_DELIVERY_SCRIPT`）、处理输入映射、动画切换、受伤反馈、死亡逻辑。

**风险：** 每新增一种 delivery 类型或元素类型，都要改 Player。

**建议：** 抽取 `DeliveryDispatcher` 组件，将 `_on_execution_activated` 中的类型判断逻辑移出 Player。

```gdscript
# 新文件: combat/delivery/delivery_dispatcher.gd
class_name DeliveryDispatcher
extends Node

@export var content_catalog: RunContentCatalog

func spawn_delivery_for_snapshot(
    snapshot: SkillExecutionSnapshot,
    spawn_info: DeliverySpawnInfo
) -> DeliveryBase:
    var content = content_catalog.content_for(snapshot.skill_id)
    if content == null or content.runtime_delivery_scene == null:
        return null
    var node = content.runtime_delivery_scene.instantiate()
    # 通过协议方法初始化，而非 is 类型判断
    if node is DeliveryBase:
        node.initialize_delivery(...)
        return node
    node.free()
    return null
```

**优先级：高 | 改动量：中 | 影响范围：仅 player.gd + 新建文件**

### 问题 2：RelicEffectRegistry 违反开闭原则

**现状：**

```1:18:combat/relics/relic_effect_registry.gd
static func create_effect(effect_kind: RelicDefinition.EffectKind) -> RelicEffect:
	match effect_kind:
		RelicDefinition.EffectKind.FORM_SWITCH_ENERGY_RESTORE:
			return FormSwitchEnergyEffect.new()
		RelicDefinition.EffectKind.REACTION_ENERGY_RESTORE:
			return ReactionEnergyEffect.new()
		# ... 每新增一种遗物类型就要在这里加一个分支
```

**风险：** 每次新增遗物类型需要改这个文件，容易遗漏。

**建议：** 改为注册表模式，让每种 Effect 自己注册自己的创建方式。

```gdscript
# 新结构
class_name RelicEffectRegistry
extends RefCounted

static var _registry: Dictionary[RelicDefinition.EffectKind, Callable] = {}

static func register(kind: RelicDefinition.EffectKind, creator: Callable) -> void:
    _registry[kind] = creator

static func create_effect(effect_kind: RelicDefinition.EffectKind) -> RelicEffect:
    if _registry.has(effect_kind):
        return _registry[effect_kind].call()
    return null

# 在每种效果的定义文件中自注册（类似 autoload 的 _ready）
# FormSwitchEnergyEffect.gd
static func _static_init() -> void:
    RelicEffectRegistry.register(
        RelicDefinition.EffectKind.FORM_SWITCH_ENERGY_RESTORE,
        func(): return FormSwitchEnergyEffect.new()
    )
```

**优先级：中 | 改动量：小 | 影响范围：relic_effect_registry.gd + 各 effect 文件**

### 问题 3：RunContentCatalog 验证逻辑过于集中

**现状：** `run_content_catalog.gd` 第 166-243 行的 `_runtime_delivery_validation_error` 包含大量 `if execution is X` 类型判断 + 对应的 delivery 场景验证逻辑。

**风险：** 新增执行类型需要同时改这里。验证逻辑应该分散到各自的执行定义中。

**建议：** 将 delivery 验证责任下放给 `SkillExecutionDefinition`：

```gdscript
# 在 SkillExecutionDefinition 基类中添加虚方法
func validate_delivery_scene(scene: PackedScene) -> StringName:
    return &""  # 默认不需要 delivery

# InstantDeliveryExecution 重写
func validate_delivery_scene(scene: PackedScene) -> StringName:
    if scene == null: return &"missing_runtime_delivery_scene"
    var root = scene.instantiate()
    var ok = root is DeliveryBase
    root.free()
    return &"" if ok else &"delivery_protocol_mismatch"
```

然后 Catalog 只需要：
```gdscript
var delivery_error = skill.execution_definition.validate_delivery_scene(content.runtime_delivery_scene)
```

**优先级：中 | 改动量：中 | 影响范围：skill_execution_definition.gd + 子类 + catalog**

### 问题 4：新增技能的摩擦成本仍然偏高

**现状：** 添加一个新技能需要：
1. 创建 `SkillDefinition` (.tres)
2. 创建 `AttackPayloadDefinition` (.tres，作为 sub_resource)
3. 创建 `SkillContentDefinition` (.tres)
4. 可能创建新的 delivery 场景 (.tscn)
5. **手动**编辑 `run_content_catalog.tres` 添加引用
6. 如果是新执行类型，还要改多个验证点

**建议：** 提供 Python 脚本自动批量生成技能资源文件。

```python
# scripts/tools/generate_skill.py
"""
用法: python generate_skill.py --id ice_spike --name "冰锥" --energy 30 --damage 1.2 \
    --element ice --slot active_2 --cooldown 0.5
"""
import argparse, json

def generate_skill_resource(args):
    # 自动生成 .tres 文件
    pass

def register_in_catalog(catalog_path, skill_content_path):
    # 自动添加到 run_content_catalog.tres
    pass
```

**优先级：中 | 改动量：小 | 影响范围：新增工具脚本**

### 问题 5：元素系统扩展需要改多处硬编码

**现状：**
- `ElementIds` 只有 `WATER` / `FIRE` 两个元素，新增元素要改 `ALL` 数组、`is_combat_element`、`opposite_of`
- `WaterFireResolver` 硬编码了水/火反应逻辑
- Player 的 `_apply_element_presentation` 硬编码了颜色映射
- 动画名称硬编码为 `water_xxx` / `fire_xxx`

**建议：** 将元素配置完全数据化：

```gdscript
# 新文件: combat/definitions/element_registry.gd
class_name ElementRegistry
extends RefCounted

static var _elements: Dictionary[StringName, ElementDefinition] = {}
static var _reactions: Dictionary[StringName, Dictionary[StringName, Callable]] = {}

static func register(def: ElementDefinition) -> void: ...
static func register_reaction(a: StringName, b: StringName, resolver: Callable) -> void: ...
static func resolve_reaction(incoming: StringName, carrier: ElementSnapshot) -> ElementResolution: ...
```

**优先级：低（当前只有 2 种元素） | 改动量：大 | 影响范围：全局**

---

### 问题 6：Slot 系统扩展需要改多处

**现状：** `SkillSlotIds` 定义了 4 个槽位（`active_1/2/3` + `passive_1`）。新增槽位需要改：
- `SkillSlotIds.all()` 返回值
- `SkillLoadout.shared_validation_error()` 期望的槽位数
- `RuntimeSkillLoadout` 的槽位遍历
- 输入映射（`project.godot`）
- UI 显示

**建议：** 将槽位配置放入 Resource：

```gdscript
# SlotConfig.tres
class_name SlotConfiguration
extends Resource

@export var slot_id: StringName
@export var slot_kind: SlotKind  # ACTIVE / PASSIVE
@export var input_action: StringName
@export var display_order: int
```

**优先级：低（当前 4 槽够用） | 改动量：中 | 影响范围：loadout + input + UI**

---

### 问题 7：被动技能缺乏统一的注册机制

**现状：** `PassiveEffectDefinition.create_runtime()` 返回 null（基类实现），每个子类自己实现。但 `RunContentCatalog._runtime_delivery_validation_error` 中对 `BurningPassiveEffectDefinition` 和 `UnendingPassiveEffectDefinition` 做了硬编码检查。

**建议：** 让被动效果定义自带验证逻辑，而不是在 Catalog 里做类型判断。

## 六、总结

项目的架构基础**显著优于平均水平**——特别是技能的三层 Resource 设计、Contract 数据对象层、Delivery 生命周期管理、Signal 驱动的组件通信。这些设计决策使得核心战斗循环非常健壮。

主要改进空间在于**"最后一英里"的扩展便利性**：当前架构支持数据驱动，但注册和验证仍依赖手动编辑和硬编码类型判断。上述 P0/P1 改进可以将新增技能的摩擦从"改 5+ 处代码"降到"只创建资源文件"。
