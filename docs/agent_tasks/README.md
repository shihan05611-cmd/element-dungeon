# Agent 任务文档规则

本目录只管理已明确立项的 Agent 任务。

中枢 Agent 的职责、对话复用、任务分发、`wait_threads` 主动跟踪、单行冻结回执、Git 与安全规则统一见 `docs/agent_tasks/CENTRAL_REVIEW_RULES.md`。执行与 Review 对话只在各自任务内保存完整交付并冻结，随后向当前中枢发送一次固定格式的单行唤醒回执；不得跨对话重复发送文件清单、日志或完整交付。Review Agent 按 `docs/agent_tasks/REVIEW_AGENT_RULES.md` 选择 L1/L2/L3；只有 L3 必读 `docs/agent_tasks/REVIEW_L3_PLAYBOOK.md`。本 README 主要保留任务文档格式、项目通用 UI 口径、当前依赖和历史基线。

## 协调优先级

- 项目执行与 Review 采用风险匹配：不缩减所选等级的必要覆盖，也不把简单任务机械升级为发布级 L3。
- 默认 Review Level 为 L2；边界清楚的低风险任务可明确使用 L1，公共接口、随机/不稳定、跨域、性能或发布检查点使用 L3。
- 对话按职责长期复用，任务书按任务编号拆分；只有对应职责对话的上下文压力可能影响准确性时，才新开接替对话并完整交接。所有中枢、执行、恢复和独立 Review 分发默认强制显式指定 `model: gpt-5.6-sol`，复用对话时也须在本次消息重新指定；模型与推理等级是独立字段，禁止只写推理等级后继承默认模型，禁止自动降级到 `gpt-5.3-codex-spark`。仅用户可明确覆盖；5.6 不可用时停线回报。
- 中枢 Review 分发执行、恢复或独立验收任务时，优先先创建或更新对应的 Markdown 任务书，并以该文档作为正式派发载体；聊天消息只作提醒或补充，不应成为唯一任务来源。
- 任务书应持续记录目标、背景、依赖、状态、文件边界、禁止事项、验收条件、证据路径、交付结论和重要变更，使后续复盘可追溯，也让新 Agent 无需依赖旧对话即可快速理解此前工作。

## 显示分辨率统一口径

- 数据基准：Steam Hardware & Software Survey（2026-06）中，主显示器 `1920×1080` 占 `51.12%`、`2560×1440` 占 `21.44%`、`2560×1600` 占 `5.64%`、`3840×2160` 占 `4.95%`、`3440×1440` 占 `3.09%`、`1366×768` 占 `2.32%`。
- 项目继续使用 `1152×648` 作为 16:9 逻辑画布；它不是目标玩家的物理分辨率。正式设计稿、截图和视觉判断以 `1920×1080` 为第一基准，以 `2560×1440` 为第二基准。
- UI 验收按 Review Level 分级：L1 查看 1～3 张最能证明改动的实际画面；L2 至少检查 P0 `1920×1080`、`2560×1440` 与一个直接相关边界；L3 才默认完整验证 P0、P1 `1366×768`/`2560×1600`/`3840×2160` 和 P2 `3440×1440` 的边界与安全区。任务书可用程序化断言替代重复截图，但不得省略对应风险检查。
- `900×540` 只作为极限窗口/回归压力测试，不再作为主要设计目标，也不得为了通过它牺牲 1080p/1440p 的比例、字号或表现力。
- 当前项目使用 `canvas_items + expand`；HUD 必须使用逻辑画布、Control 锚点/容器和内容缩放换算，禁止把原始物理窗口坐标直接当作 UI 坐标。
- 16:10 与超宽屏应扩展战场可见区域；核心 HUD 保持锚定和可读，不横向拉伸。中央关键内容留在 16:9 安全框内，边缘信息可锚定实际屏幕边缘。
- 4K 验收重点是 UI 物理可读尺寸、缩放一致性和纹理清晰度，不为 4K 单独重排玩法信息。

## 目录

- `pending/`：尚未完成验收的任务，包括待开始、进行中、阻塞和待复核状态。
- `completed/`：已经由协调者复核并明确验收通过的任务。

## 生命周期

1. 每轮新需求必须创建新的任务文档，不得覆盖或重新打开上一轮已完成任务。
2. 任务文档必须写明负责人、依赖、独占文件范围、禁止修改范围和验收条件。
3. 任务文档必须标注 `Review Level: L1 / L2 / L3`；未标时按 L2，Review 可因明确风险输出 `ESCALATE`。
4. 执行 Agent 完成后提交与等级匹配的测试证据，但不能自行把任务标记为已验收。
5. Review 通过后，由协调者将任务文档移入 `completed/`。
6. 后续回归问题使用新的任务编号；旧文档只作为历史事实保留。

## 状态字段

任务文档顶部统一使用：

```text
状态：PENDING / IN_PROGRESS / BLOCKED / REVIEW / ACCEPTED
负责人：Agent X
依赖：任务编号或“无”
Review Level：L1 / L2 / L3
升级触发：公共接口、随机/不稳定、跨域、性能或本任务的其他具体条件
```

只有 Review 通过后才能使用 `ACCEPTED`。

## 版本管理

- 任何需要修改游戏项目文件（代码、场景、资源、配置、正式资产）的工作，严禁使用当前对话内的子 Agent；必须派发到独立可见的执行职责对话并完成任务书交接。同一职责对话跨任务长期复用，只有上下文压力影响准确性时才新开接替对话。子 Agent 仅可用于不会写项目的研究、资料整理或只读取证。
- 执行 Agent 不执行 Git 写操作；只负责实现、测试并报告修改文件、测试结果和未解决问题。
- Review Agent 使用与执行者隔离的独立 Review 职责对话；该对话也按职责长期复用，不要求每个任务新开。执行者不得自验收。
- 中枢负责阶段性版本检查点：在一组相互依赖的交付完成分级独立验收、工作树范围核对和必要回归后提交 Git。提交频率按可恢复的阶段变化决定，不按每个 Agent 或每个任务机械提交。
- 中枢提交前必须核对文件 allowlist、排除未验收或来源不明的改动，并在提交说明中记录对应任务与验证基线。
- `reset`、`restore`、`checkout`、`clean`、删除或覆盖等恢复操作必须先完成只读审计并明确目标；不得把整个脏工作树一键恢复到旧提交。
- 若发现任务文件与其他正在进行的工作重叠，停止覆盖并报告协调者。
