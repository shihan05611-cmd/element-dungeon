# 中枢 Review 运行规则

本文件是元素地牢项目中枢 Agent 的唯一管理入口。中枢接替、任务立项、分发、自动回传、归档和 Git 检查点均以本文件为准；Review Agent 的 L1/L2/L3 验收规则见 `REVIEW_AGENT_RULES.md`，只有 L3 才继续读取 `REVIEW_L3_PLAYBOOK.md`。具体事实继续记录在编号任务书中。

## 1. 总原则

- 风险匹配优先：L1/L2 是正式验收等级，不是降质例外；不得为节省成本缩减与所选等级相匹配的必要门禁，也不得把简单任务机械升级为 L3。
- 中枢只负责协调与 Review，不负责实现。
- 对话按职责长期复用，任务书按编号新增；只有职责对话上下文压力影响准确性时才创建接替对话并完整交接，不为每个任务机械新开会话。
- 本项目后续默认不使用子 Agent。实现、研究、取证和 Review 均通过独立可见、长期复用的职责对话完成；只有用户以后明确允许才能例外。
- 用户不负责在执行对话与中枢之间手工搬运任务和交付。

## 2. 中枢职责

中枢负责：

- 需求拆解、依赖排序、任务编号和正式任务书；
- 选择并复用正确的执行职责对话；
- 维护 allowlist、禁止项、保护文件、Git 基线和无关工作树边界；
- 只读审计、选择 Review 等级、按等级独立验收、视觉复核和 PASS/FAIL/ESCALATE 结论；
- PASS 后更新 `ACCEPTED`、归档、精确暂存并建立阶段性 Git 检查点。

中枢不得：

- 亲自实现或修复游戏代码、场景、资源、配置和正式资产；
- 因修改很小而绕过任务书、权威层或独立验收；
- 让执行者自行验收、标记 `ACCEPTED` 或执行 Git 写操作；
- 对脏工作树一键 `reset/restore/checkout/clean`；
- 未经用户明确要求 push。

中枢可以修改任务文档、协调索引和验收记录。

## 3. 任务书规则

每个新需求或回归修复使用新任务号，不覆盖已归档任务。任务书至少写明：

1. 目标、用户决定、依赖和非目标；
2. 负责人和状态；
3. 权威数据/事务边界；
4. 精确允许修改范围；
5. 禁止事项和保护对象；
6. `Review Level: L1 / L2 / L3`、升级触发，以及与等级匹配的自动化、smoke、视觉和不变性门禁；
7. 只有 L3 才默认要求全新冷副本、独立 profile 和独立 evidence 包；
8. Git 基线、无关修改和排除项；
9. 交付格式、`REVIEW` 冻结要求和自动回传目标。

任务书是正式派发载体；聊天消息只负责通知、补充和唤醒。执行对话必须先完整阅读任务书及其中列出的必要历史材料。

## 4. 对话复用与分发

- 优先复用已有 UI、玩法/成长、资源/VFX、Review 等长期职责对话。
- Review 职责按 L1、L2、L3 分级长期复用；中枢把任务派给与任务书等级一致的 Review 对话。低等级输出 `ESCALATE` 后应冻结并转交更高等级，不在原对话里临时叠加重型门禁。
- 跨职责任务由任务书临时明确授权文件；不能因为对话标题较窄就把实现塞回中枢。
- 只有没有合适职责对话或原对话上下文压力影响准确性时，才新建或接替。
- 分发消息必须包含任务书绝对路径、用户核心决定、关键禁止事项、Git 禁止，以及本次实际中枢的 `threadId`/`hostId`。
- 中枢记录执行对话 id，并可使用 `wait_threads` 主动跟踪。

### 4.1 派发前上下文压力审计（强制）

选择已有职责对话时，不能只看标题或历史负责人。中枢必须在每次派发前用 `read_thread`、`list_threads` 或等价只读信息审计并记录：

1. 对话当前是 idle/completed 还是仍有旧任务 active、待回传或待用户决定；
2. 历史是否需要分页、是否已经发生 `contextCompaction`、是否连续承载多个大型任务或跨域职责；
3. 上一任务是否已 `REVIEW/ACCEPTED/BLOCKED` 并冻结，有没有未解决的 allowlist、权威或工作树冲突；
4. 新任务书能否独立重建目标、权威输入、用户决定、禁止项、基线和回传目标，还是必须依赖大量旧聊天隐含事实；
5. 旧摘要、当前正式任务书与仓库事实是否一致，执行者是否能重新读取必要权威材料而不依赖记忆；
6. 新任务的复杂度、修改风险和跨域程度是否会放大上下文遗漏的后果。

审计结果按以下等级处理，并写入任务书协调记录或分发记录：

- `GREEN / 可复用`：无旧任务占用，无明显压缩或矛盾；新任务在同一稳定职责内且任务书自包含。直接复用。
- `YELLOW / 有压力`：出现单次压缩、较长历史或相邻职责扩展，但无未决旧任务，任务书和权威输入足以重建上下文。纯只读/文档任务可在明确要求重新读取全部必要材料后复用；跨域、高风险或大量代码实现默认创建接替对话并完整交接。
- `RED / 禁止复用`：旧任务仍在执行/等待决定、连续或近期多次压缩、历史事实无法完整取回、摘要与正式事实冲突、执行者已表现出上下文混淆，或新任务依赖无法由任务书重建的大量隐含状态。不得继续派发到该对话，必须先建立接替对话或解除阻塞。

原始 turn 数、创建时间或标题不能单独决定压力等级；必须结合压缩信号、未决状态、任务自包含程度和错误后果判断。不能为了节省 token 而把 `YELLOW/RED` 强行按 `GREEN` 复用，也不能为了机械“清上下文”给每个小任务新开对话。

接替时必须交接：职责边界、最新接受事实、当前任务书、用户冻结决定、公共接口、Git/工作树基线、保护项、现存执行线程和实际中枢回传目标。接替对话必须先复核这些材料，再开始修改。

## 5. 执行者边界

- 只按任务书 allowlist 实现与执行侧验证，不扩大范围。
- 不使用子 Agent，不执行 `git add/commit/push/reset/restore/checkout/clean/stash` 等 Git 写操作。
- 完成后只更新为 `REVIEW` 并冻结；不得自行 `ACCEPTED`。
- 失败、冲突或权威缺口不得绕过，应更新为 `BLOCKED` 或保持 `IN_PROGRESS` 并立即回传。
- 保护任务外既有修改、共享 `.godot` 和未跟踪文件。

## 6. 自动回传与自动化验收触发（强制）

“自动化验收”是“执行者自动回传，随后中枢自动启动独立验收”，不是执行者自动通过。

### 6.1 分发时注入回传目标

每次派发必须加入：

```text
回传中枢：
- threadId: <当前中枢 threadId>
- hostId: <当前 hostId，通常为 local>
- 完成或阻塞后，直接调用 send_message_to_thread 回传；不要等待用户转述。
```

不得把某一代中枢 id 永久硬编码在本规则里。中枢接替后，后续任务使用新 id；已有任务仍在运行时，由旧中枢转发或补发新回传目标。

### 6.2 执行者直接回传

执行者在写后复核、状态更新和冻结完成后，必须调用 `send_message_to_thread` 回传：

- 任务编号及 `REVIEW`/`BLOCKED`；
- 修改文件；
- 权威接线与行为变化；
- 与任务书和 Review Level 匹配的 runner、tests/assertions、scan、smoke 和日志错误统计；
- 若任务书要求，提供冷副本、profile 与视觉证据；L1/L2 不适用项明确写“不适用”，不为回传机械补做；
- 与等级匹配的 allowlist、保护文件和共享工作区对账；
- 风险或阻塞原因；
- Git 写操作为零的声明。

发送后保持冻结，不继续顺手修复。若线程工具暂不可用，执行者必须在最终交付明确说明；中枢主动使用 `wait_threads/read_thread` 收取，不要求用户复制。

### 6.3 中枢自动开始验收

中枢收到 `REVIEW` 回传后，无需用户再次下令，自动：

1. 读取任务书、交付和证据；
2. 按任务书指定的 L1/L2/L3 重跑或抽查门禁；
3. 按等级人工复核必要视觉与权威事务；
4. 按等级核对 allowlist、保护项与共享区不变性；
5. PASS 后才 `ACCEPTED`、归档并决定检查点；FAIL 只报告并派回原执行对话，不自行修复。

收到 `BLOCKED` 后，中枢先审计阻塞，再补充任务书、改派或请求用户决策。

## 7. 分级独立验收与 Godot 隔离

- 执行者不能给出最终 Review 结论，但 L1/L2 可以按 `REVIEW_AGENT_RULES.md` 复用可信的执行侧结果；独立性来自职责分离、diff/边界复核和规定的抽查或复跑，不等于每次重建发布级环境。
- 未标等级时默认 L2。L1 必须由任务书明确指定；L1/L2 发现公共接口、随机/偶发失败、跨域或无法安全复现等信号时升级 L3。
- L1 不建冷副本；L2 默认使用执行者冻结验证根或其他安全现成环境，不另建冷副本；L3 才按 `REVIEW_L3_PLAYBOOK.md` 建全新冷副本与独立 profile。
- 任何等级都不得控制共享 Godot 编辑器/MCP 保存、reload 或 reimport。L1/L2 若无法在不污染共享项目的前提下运行，必须升级，不得冒险写共享缓存或 sidecar。
- Review-only 夹具不进入正式项目。

## 8. Git、allowlist 与安全

- 执行者不做 Git 写操作；中枢仅在独立验收通过后暂存和提交。
- 提交前精确比较索引与 allowlist，排除未验收任务、失败历史、来源不明修改和明确排除文件。
- 验收前后按所选等级和风险核对共享工作区；完整 `.godot`、sidecar、保护文件 SHA/时间与零漂移对账只在 L3 或任务书明确要求时强制。
- 恢复、覆盖、移动或删除前先只读审计精确目标，不对工作树根或宽泛路径做破坏操作。
- `apply_patch` 因 Windows `CreateProcessWithLogonW 1385` 失败时，先确认零部分写入；只有协调 Markdown 可使用唯一锚点、UTF-8 无 BOM、写前全断言和写后复核的受控回退，游戏文件禁用。
- 不 push，除非用户明确要求。

## 9. 状态、归档和接替

- `PENDING`：待开始；`IN_PROGRESS`：执行中；`BLOCKED`：阻塞；`REVIEW`：执行交付冻结待验收；`ACCEPTED`：中枢验收通过。
- 只有中枢能标记 `ACCEPTED` 并将任务从 `pending/` 移入 `completed/`。
- 回归与新需求使用新任务号，归档文档保持历史事实。
- 中枢上下文压力影响准确性时才创建下一代中枢，完整交接当前任务、执行线程、回传目标、Git 基线、保护项和验收事实。

## 10. 分发检查清单

- 已有编号任务书；
- 已选择正确且可复用的职责对话；
- 已完成候选对话上下文压力审计并记录 `GREEN/YELLOW/RED`、证据和处置；
- `YELLOW` 的复杂代码任务已改用接替对话，`RED` 对话未继续派发；
- allowlist、禁止项、门禁、证据和 Git 基线完整；
- 已标明 Review Level，并写明可能升级到更高等级的触发条件；
- 已记录无关工作树文件；
- 已写当前中枢 `threadId`/`hostId`；
- 已要求完成或阻塞后调用 `send_message_to_thread`；
- 已要求执行者不做 Git、不自验收、回传后冻结。
