## 2. 冻结规则与权威边界

- 固定共享槽位仍为 `ACTIVE_1 / ACTIVE_2 / ACTIVE_3 / PASSIVE_1`，不得增加、删除或按元素拆分。
- `CurrentElement`、能量、冷却、忙碌、锁定、失败原因、目标水/火层数都只消费既有权威状态或信号。
- UI 不得自行选择游戏目标。目标跟随标签只能绑定既有权威锁定/目标；没有可定位的权威目标时使用固定回退或隐藏。
- 继续维持单一最终伤害数字；反应倍率和实际消耗层数只能作为次级提交后反馈。
- `RewardGenerator.MAX_OPTIONS = 3` 是上限而非 UI 强制数量。奖励 UI 必须按权威 offer 的实际 1/2/3 项动态布局，不补假候选，不改变候选池、随机、事务或领取规则。
- “与当前构筑关系”只能展示已拥有、已装备、槽位合法性、奖励类型、技能类型、元素策略等已有权威字段；不得新增战力、协同、推荐度或替换收益评分。
- 没有权威稀有度、重随、取消领取或返回上一步能力时，不得为了界面完整而伪造。
- UI 不拥有 SkillExecutor、Delivery、Targeting、CombatResult、RuntimeLoadout、RunSession、ShopDraft 或 Growth 规则。

## 4. 战斗 HUD 正式规格

目标画布为 `1152×648`，下限为 `900×540`。必须使用可响应的 Control 容器、锚点和断点规则，不能只为一张截图硬编码绝对位置。

### 4.1 1152×648 主布局

- 左上生存胶囊：基准 `(16,16) 280×76`。
  - 只常驻 HP、能量、低生命警示；
  - 数字使用稳定宽度，条形变化不得推动其他控件；
  - 角色名、长状态句和调试字段不常驻。
- 底部居中技能带：基准 `(304,560) 544×72`。
  - 顺序固定为 `CurrentElement / A1 / A2 / A3 / P1`；
  - CurrentElement 必须成为可辨识的元素枢纽，采用形状、短文字与颜色冗余编码；
  - ACTIVE 只常驻图标、键帽、冷却遮罩/秒数和必要短状态；
  - PASSIVE 使用不同外形或缺口边框，不能伪造释放键或冷却。
- 顶部短时反馈：基准 `(396,18) 360×36`，只显示提交后成功/失败/切换和恢复动作，不能与常驻教程争用。
- 操作帮助不再占据常驻面板；首次进入或设置切换后可短时回显，不能新增 `project.godot` 输入项。
- 无目标时不显示空的 Target 面板。

常驻包围盒目标不高于画面 `8.5%`；固定目标回退出现时不高于 `10%`；短时反馈同时出现的理论峰值不高于 `11.5%`。交付证据必须写出实际测量矩形和计算方式。

### 4.2 技能与状态语法

- 可释放、冷却、能量不足、忙碌/Channel、元素锁定、失败必须能在不读取长句的情况下区分。
- 冷却同时使用遮罩与数字；`0.0–9.9` 可显示一位小数，大于等于 10 秒显示整数。
- 能量不足使用资源 glyph/缺口与短词，不只降低透明度。
- 忙碌可用技能带公共状态条 + 被拒槽短词，不在四槽重复长句。
- 元素固定/当前/无属性不得只靠颜色；必须有形状或短标识。
- 失败提示写清原因和可恢复条件，但不把内部 snapshot/debug 信息泄露到正式 HUD。
- PASSIVE 触发只作短时强调；不移动其他槽位。

### 4.3 目标元素层数

- 有可定位的权威目标时，水/火附着标签跟随目标，最大约 `156×48`，与敌人血条/关键预警保持安全间隔。
- 目标离屏、贴边或无法可靠定位时，回退到右上固定区域；回退仍显示目标身份所需的最小上下文和水/火层数。
- 目标失效、死亡、换房或权威目标切换时必须正确清理/重绑，不能残留旧层数。
- 多目标场景不自行按距离、朝向或可见性挑选目标；只消费现有权威目标信号。没有权威目标时宁可隐藏，不引入 UI 目标规则。
- 减少动态模式下不平滑追踪、不弹跳，使用稳定位置或固定回退。

## 5. 奖励选择正式规格

### 5.1 1152×648

- 主比较区基准 `(56,72) 1040×504`。
- 三项时使用三张约 `328×344` 等宽卡；两项时等宽居中；一项时单卡居中。
- 卡片字段按权威可用性固定顺序：
  1. 序号/焦点；
  2. 图标与名称；
  3. 奖励类型、主动/被动、元素策略；
  4. 一句话效果；
  5. 能耗/冷却或触发条件；
  6. 权威构筑状态 chips。
- 缺少某个权威字段时收起该行，不能从 ID、颜色或描述文本猜测。
- 卡片底部保留统一操作安全区，长文本不能挤掉确认路径。

### 5.2 焦点与提交

- 键盘/手柄焦点顺序按实际候选从左到右，再到确认和权威允许的返回/取消。
- 首次选择只改变聚焦候选；独立确认才调用既有奖励提交事务，防止导航时误领。
- 一项候选仍需显式聚焦和确认，不能自动领取。
- 提交中避免重复输入；提交失败显示权威失败原因并保留可恢复焦点；成功后沿用既有状态推进。
- 鼠标、键盘和手柄不得依赖 hover 才能看到候选类别或核心效果。

### 5.3 900×540

- 外边距降为 12 px；生存胶囊约 `236×68`，技能带约 `500×68`。
- ACTIVE 图标保持约 36 px，焦点/交互热区不小于 44 px。
- 奖励区约 `(24,32) 852×476`；三卡约 `268×320`，间距 12 px。
- 20/40/80 个中文字符和长英文名均不得横向越界；优先摘要、换行和聚焦详情，不把正式正文降到 12 px 以下。

## 6. 视觉质量与可访问性

- 只借鉴任务 19 的信息组织原则，不复制《死亡细胞》《哈迪斯》《暖雪》《小骨》的具体图标、字体、边框、配色、肖像或装饰。
- 使用项目已有正式技能图标；没有图标的系统状态使用一致的 Godot 原生矢量/绘制语法，不用 emoji 或来源不明占位。
- 建立统一 UI tokens：8 px 间距节奏、有限圆角/描边层级、P0/P1 字号、语义色、遮罩与焦点样式；避免每个控件独立硬编码随机值。
- 普通文本对比至少 `4.5:1`，较大 glyph/边界至少 `3:1`。
- 水/火、可用/冷却、成功/失败均不得只靠颜色；色觉辅助模式下要有形状和文字。
- 微交互建议 `150–220 ms`，只表达状态变化；不使用无意义循环动画。
- 减少动态模式下禁止位移、缩放、闪烁和持续脉冲，语义与时序仍完整。
- 视觉表现必须与任务 17/18 VFX 协调：HUD 不遮挡核心战斗区，不能重绘或复制技能 VFX。

UI/UX 规范只采纳与 Godot 战斗界面相关的原则：渐进披露、稳定布局、44 px 焦点/交互目标、可见焦点、颜色冗余编码、150–300 ms 有意义动效和减少动态。不得照搬通用网页模板、字体或配色建议。
