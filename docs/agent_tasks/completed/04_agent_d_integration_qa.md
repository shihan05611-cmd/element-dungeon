## 3. 冻结规则总表

### 3.1 元素

- 只实现水、火。
- 元素量为整数层，每种元素范围 `0..10`。
- 同元素累加至 10。
- 附着不自动衰减；反应消耗、死亡或离开房间时清除。
- 反应后未消耗的来袭元素继续附着。

```text
consumed = min(target_opposite_amount, incoming_amount)
multiplier = 1.0 + 0.3 * consumed
```

- 水火顺序对称。
- 最大反应消耗 10，最大倍率 4.0。

### 3.2 命中

- MVP 只允许敌对目标。
- 闪避、格挡、无敌、阵营非法、重复命中时伤害和元素都不生效。
- 合法命中即使最终伤害为 0，元素仍可附着。
- 无 DamageReceiver 可以只附着；无 Carrier 可以只伤害；两者都无则拒绝。
- AOE 对每个目标使用完整元素量。
- 不同 `hit_index` 是合法多段，每段使用完整配置元素量。

### 3.3 技能与快照

- 水火技能槽相互独立。
- 能量和特殊冷却在 Cast 被接受时消费/开始；打断不退款。
- 常规技能冷却为 0。
- 施法时允许切换形态，但当前 Cast 和已生成 Delivery 保持原元素与攻击快照；下一 Cast 才使用新形态。
- 施法者攻击属性在 Cast 接受时锁定；目标防御在命中时读取。
- 反应和击杀归触发攻击的 `root_owner_id`。

### 3.4 伤害与通知

```text
offensive_damage
→ 乘以水火反应独立倍率
→ 目标防御
→ max(0)
→ roundi 一次
```

- 所有战斗状态静默写入完成后才能发出表现、UI、生命变化和死亡通知。
- UI、动画、音效只读取 `CombatResult`，不得反向参与规则。

## 8. 战斗内 UI/UX 范围

本阶段不制作主页、选关、设置页，也不实现“主页 → 游戏”的跳转。项目仍从测试房间直接进入战斗。UI 工作只覆盖游戏内 HUD、战斗反馈和调试信息。

### 8.1 层级与场景结构

建议拆为两个表现层：

```text
CombatUI (CanvasLayer，固定屏幕 HUD)
├── PlayerStatus
│   ├── HealthBar
│   ├── EnergyBar
│   └── CurrentElement
├── SkillStatus（最小槽位/按键提示，可简化）
└── DebugOverlay（默认隐藏，可切换）

WorldFeedbackLayer
├── DamageNumber
├── ReactionLabel
└── ResourceWarning
```

- HUD 必须独立于 Camera2D 移动，并适配当前 `1152×648` 视口及项目 stretch 设置。
- 使用锚点、容器和安全边距，不依赖散落的绝对坐标。
- 世界飘字使用命中世界坐标转换到正确显示层；镜头移动时不得明显漂移或跳位。
- UI 只能订阅 Agent A/B 提交后的结果和状态通知，不得每帧反向改写生命、能量、元素或技能状态。

### 8.2 首版常驻 HUD（必做）

左上角设置玩家状态区，信息优先级为“生命 > 能量 > 当前元素”：

- **生命条**：始终显示，包含图形条和 `当前/最大` 数值，例如 `86 / 100`。
- **能量条**：位于生命条下方，包含图形条和 `当前/最大` 数值。
- **当前元素**：显示水/火图标或形状、文字“水/火”和语义颜色；不得只靠颜色区分。
- **技能状态**：首版只需最小槽位、按键或可用/不可用状态，不要求完整技能栏美术。
- 普通敌人暂不需要常驻屏幕 Boss 血条；木桩/当前测试目标的生命与元素层数可放进 DebugOverlay。

视觉基调采用暗色地牢上的紧凑像素/游戏 HUD：

- HUD 底板使用足够不透明的深色衬底，保证明暗场景中均清晰。
- 生命使用高辨识危险色，能量使用与生命明显不同的颜色；水为青蓝、火为橙红，但同时配文字/图形。
- 数字使用稳定宽度或固定最小宽度，数值变化不得推动其他组件左右跳动。
- 正文和关键数字在底板上的对比度目标不低于 4.5:1。
- 不下载或擅自引入外部字体；优先使用工程现有字体/主题并保证中文可读。

### 8.3 血量与能量反馈（必做）

- 生命和能量以组件实际值为唯一数据源；HUD 不自行推算。
- 扣血时生命条立即反映真实值，可增加 0.25–0.45 秒的延迟损失条，但延迟条不得冒充真实生命。
- 生命低于 30% 时增加形状、边框或文字提示，不能仅将颜色变红。
- 消耗能量时用 150–250ms 的填充变化或短促闪光表达，不改变控件布局。
- 能量不足导致释放失败时，能量条短促脉冲，并显示一次简短“能量不足”；相同提示需限频，避免按住按键时刷屏。
- 形态切换用 150–250ms 的图标/文字过渡；当前 Cast 和飘字颜色仍读取其锁定元素，不随玩家新形态改变。
- 纯表现动画不得阻塞输入或影响技能状态机；需能被新状态立即打断。

### 8.4 伤害飘字与反应提示（必做）

伤害飘字必须由提交成功后的 `CombatResult` 生成，显示 `final_damage`，不得根据基础伤害自行计算。

- 生成位置使用实际命中世界坐标；同一已提交结果只能生成一次。
- 普通伤害使用高对比浅色数字；水/火伤害可使用青蓝/橙红轮廓或小型元素标记。
- 水火反应的最终伤害数字提高一级字号/缩放，并附短标签“反应”或统一反应标记；不要再额外显示一个会被误认为第二次伤害的数字。
- 玩家受到伤害时使用与敌人伤害可区分的样式或方向。
- 格挡、无敌或整体拒绝时不显示 `0` 伤害；如需要反馈，显示一次“格挡/无效”，并与伤害数字样式区分。
- 只附着元素而未造成伤害时，正式 HUD 默认不显示伤害数字；DebugOverlay 可以显示元素 delta。
- 多段攻击每个成功的 `CombatResult` 可以各显示一次；同帧大量数字应使用稳定偏移/轻微错位避免完全重叠。
- 建议生命周期 0.6–0.9 秒：快速出现、缓慢上浮、淡出；进入使用 ease-out，退出使用 ease-in。
- 禁止长时间弹跳、全屏抖动或同时驱动大量装饰动画。预留“减少动态效果”开关：开启后保留数字和颜色，只去掉漂移/缩放。
- 对同时存在的飘字设置合理上限（建议 24–32）；超限时合并或回收最旧的纯表现节点，不能影响战斗结算。

### 8.5 战斗反应 UX（必做）

- 命中反馈由角色闪白/受击动作、飘字和短促命中特效共同表达，避免三个系统重复制造独立伤害信息。
- 反应发生时只增加一个清晰层级：较强数字样式 + 反应标签/特效；不要求额外全屏提示。
- 技能不可用必须有原因反馈：能量不足、冷却中、形态不符至少能在 DebugOverlay 中区分；面向玩家的首版重点显示能量不足。
- 颜色不是唯一信息通道：水火、低血量、格挡和反应均需要文字、形状或动画中的至少一种辅助线索。
- 所有微动画以信息传达为目的，通常控制在 150–300ms；伤害飘字因需阅读可延长至 0.9 秒。

### 8.6 正式 HUD 与调试层分离

正式常驻 HUD 只显示玩家实际需要的信息：

```text
生命
能量
当前元素
最小技能状态
战斗飘字/反应反馈
```

内部诊断信息必须放入默认隐藏、可切换的 DebugOverlay：

```text
当前技能槽/技能 ID
SkillExecutor 当前 phase
特殊技能冷却
目标生命
目标水/火元素层数（0..10）
cast_id / delivery_id / hit_index
本次反应消耗量与倍率
damage_applied / element_applied / reaction_triggered
拒绝原因
```

不要把上述内部 ID 永久堆在正式战斗画面上。

### 8.7 UI/UX 验收

- 直接运行测试房间即可看到 HUD；不存在主页或页面跳转依赖。
- 生命、能量和当前元素在进入场景时即显示正确初值。
- 扣血、扣能量、默认 5 点/秒恢复和切形态后，HUD 与组件真实状态一致；消费后等待 1 秒，暂停状态不偷跑延迟。
- 每次成功伤害只出现一个对应最终伤害的飘字；拒绝或重复命中不产生伤害数字。
- 水弹发出后切火，水弹命中的数字/元素标记仍表现为水。
- 水火反应数字层级明显，但不会被误解为结算了两次伤害。
- 暗墙、火光和高亮特效背景下均可读，关键文本/数字有足够对比度。
- 视口拉伸或窗口尺寸变化时 HUD 不跑出屏幕、不互相覆盖。
- 同屏多段/多目标攻击不会产生无限 UI 节点或明显帧尖峰。
- UI 动画被跳过、打断或设为减少动态效果时，战斗逻辑完全不受影响。

## 9. 端到端验收场景

必须自动或可重复验证：

1. 水形态释放技能命中空木桩：目标水元素正确增加。
2. 同元素继续命中：累加但不超过 10。
3. 目标火 2，水 5 命中：火归零、水剩 3、倍率 1.6。
4. 目标火 10，水 10 命中：双方归零、倍率 4.0。
5. 水弹发出后立即切火：飞行中的攻击仍是水；下一次释放为火。
6. 同一命中身份持续重叠：同目标只结算一次。
7. 不同 `hit_index`：合法多段分别结算。
8. 一次攻击命中多个目标：每个目标获得完整 Payload。
9. 高速投射物不穿墙；墙在目标之前时不隔墙命中。
10. 无 Carrier 目标正常受伤；无 DamageReceiver 目标正常附着。
11. 无敌/格挡目标不受伤也不附着。
12. 受击打断 STARTUP：能量不退款，旧回调不生成迟到攻击。
13. 两个角色共享 Skill Resource：能量、形态和冷却互不污染。
14. 目标死亡/待删除、施法者死亡、关卡退出均无失效引用和孤儿 Delivery。
15. UI、目标实际状态与同一个 `CombatResult` 一致；`final_damage` 只生成一次飘字，拒绝/重复命中不生成。
16. HUD 在 1152×648、窗口拉伸和镜头移动下保持清晰稳定。
17. 生命、能量、形态切换和能量不足反馈符合第 8 节，且 UI 动画不影响输入或结算。

## 11. 修改上游模块的限制

集成发现接口问题时：

1. 先记录最小复现和期望契约。
2. 判断问题属于 Agent A、B 还是 C。
3. 请求原所有者修改或由协调者批准后再改。
4. 禁止在 Player/Enemy 中写临时旁路绕过公共协议。

以下行为视为验收失败：

- Player 直接修改目标元素或生命。
- Projectile 内出现水火反应公式。
- 动画 Signal 承担核心结算顺序。
- 为接线重新加入全局万能 Manager。
- 修改冻结规则但未报告。
